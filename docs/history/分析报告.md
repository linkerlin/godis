# Godis 与 Redis 8.x 兼容性深度分析报告

> 分析时间：2026-06-29  
> 分析范围：协议层（RESP2/RESP3）、命令层、集群/ACL/复制/持久化、测试与 CI  
> 主要结论：**Godis 是一个“功能面很广、但深度不足”的 Redis 8.x 兼容实现。协议层尤其明显——RESP3 的“类型序列化代码”几乎都有，但没有一条端到端的 RESP3 路径。**

---

## 1. 协议兼容性：RESP2 可用，RESP3 仅“纸上实现”

### 1.1 RESP2：基本完整

`redis/protocol/reply.go`、`consts.go` 覆盖了 `+`、`-`、`:`、`$`、`*` 以及 `OK`/`PONG`/`QUEUED`/`$-1` 等 RESP2 基础类型。服务器请求解析走 `parser.ParseStream`（std）或 `ParseV2`（gnet），能处理标准 RESP2 命令数组。

### 1.2 RESP3：类型齐全但整条链路未接通

| RESP3 类型 | 是否实现序列化 | 是否实现解析 | 业务层是否使用 | 备注 |
|---|---|---|---|---|
| Null `_` | ✅ `resp3.go:43` | ✅ | ❌ | 业务仍返回 `$-1` |
| Double `,` | ✅ `resp3.go:51` | ✅ | ❌ | `ZSCORE` 等仍可能返回 Bulk |
| Boolean `#` | ✅ `resp3.go:66` | ✅ | ❌ | 未使用 |
| BigNumber `(` | ✅ `resp3.go:83` | ✅ | ❌ | 未使用 |
| Verbatim `=` | ✅ `resp3.go:99` | ✅ | ❌ | 未使用 |
| Map `%` | ✅ `resp3.go:116` | ✅ | ❌ | 键被限定为 `string` |
| Set `~` | ✅ `resp3.go:141` | ✅ | ❌ | 未使用 |
| Attribute `\|` | ✅ `resp3.go:162` | ❌ | ❌ | 遇到会报 unknown type |
| Push `>` | ✅ `resp3.go:180` / `push.go` | 部分 | ✅ 仅缓存失效 | pubsub 也用了 `PushMessage` |
| Streamed aggregates | ❌ | ❌ | ❌ | `$?/%?/~?` 未实现 |

### 1.3 协议层核心问题

1. **连接不保存协议版本**
   - `interface/redis/conn.go` 和 `redis/connection/conn.go` 都没有 `SetProtocolVersion` / `GetProtocolVersion` 字段。
   - `HELLO 3` 只是嘴上答应，后续回复格式 unchanged。

2. **服务器仍用 RESP2 解析器**
   - `redis/server/std/server.go:87` 调用 `parser.ParseStream(conn)`
   - `redis/server/gnet/server.go:79` 调用 `parser.ParseV2(c)`
   - 两者都只识别 `+ - : $ *`。客户端若按 RESP3 发命令帧，会进入 `parser.go:139` 的 `default` 分支被当作文本协议切分，导致解析错误。

3. **回复生成不根据协议版本切换**
   - `redis/server/std/server.go:121-123` 直接 `result.ToBytes()`。
   - RESP3 空值仍发 `$-1` 而不是 `_`；Map/Set/Double/Boolean 永远不会被业务命令返回。

4. **HELLO 命令只是“形式协商”**
   - `database/auth.go:150-212` 读取 `proto` 参数，但**不写入连接状态**。
   - `SETNAME` 参数仅 `_ = clientName`，没有 `c.SetClientName`。
   - 返回的 `id` 固定为 `1`，与 `CLIENT ID` 真实值不一致。
   - `execHello` 在 Lua/集群内部调用时传入 `nil` 连接，无法更新任何状态。

5. **客户端缓存失效推送：格式对、语义不全**
   - `redis/protocol/push.go:47-58` 生成的 `invalidate` push 帧格式正确。
   - 但 `REDIRECT` 只解析不生效（`database/client_conn.go:105-112`）。
   - `OPTIN/OPTOUT` 仅接受参数，`TrackKey` 未按状态过滤。
   - `NOLOOP` 未实现；未校验客户端必须已发送 `HELLO 3`；`sendInvalidation` 写错误未处理。

6. **Attribute / Streamed 类型缺失**
   - `RESP3Parser.Parse` 的 switch 没有 `\|` 分支。
   - `$? / %? / ~?` 等 RESP3 流式聚合类型完全没有实现。

> **一句话总结协议层**：RESP3 类型代码写在 `resp3.go` 里，但服务器解析、连接状态、业务回复三条路都没接上。**当前不能声称支持 RESP3。**

## 2. 命令层兼容性：广度大、深度浅、分发方式与标准客户端不兼容

### 2.1 命令分发：模块/函数命令注册方式错误

Godis 把多词命令注册成**单 bulk string**，导致标准 Redis 客户端无法调用：

| Redis 标准调用 | Godis 注册名 | 实际查找键 |
|---|---|---|
| `JSON.SET k . 1` | `JSON.Set` | `cmdLine[0] == "JSON.Set"` |
| `FT.CREATE idx ...` | `FT.Create` | `cmdLine[0] == "FT.Create"` |
| `FUNCTION LOAD ...` | `Function|Load` | `cmdLine[0] == "Function|Load"` |
| `SCRIPT DEBUG ...` | `Script|Debug` | `cmdLine[0] == "Script|Debug"` |
| `FCALL_RO ...` | `FCall|RO` | `cmdLine[0] == "FCall|RO"` |
| `VS.ADD ...` | `VSAdd` | `cmdLine[0] == "VSAdd"` |

标准 Redis 客户端会把 `JSON.SET` 拆成 `["JSON", "SET", ...]`，而 `DB.Exec` 只拿 `cmdLine[0]` 去命令表匹配，结果这些模块命令对标准客户端**全部不可见**。

### 2.2 命令标志与键位元数据错误

- `RENAME` / `RENAMENX` 在 `database/keys.go:582` 注册为 `flagReadOnly`，但实际是写命令。
- `JSON.*` / `FT.*` / `TS.*` / `BF.*` / `CF.*` / `CMS.*` / `TopK.*` / `TDigest.*` 在 `attachCommandExtra` 中 `firstKey=0,lastKey=0,keyStep=0`，与 `prepare` 实际返回的第一个键不一致，导致 `COMMAND GETKEYS` 结果错误。

### 2.3 核心命令缺失 / 差异抽样

| 命令 / 特性 | Redis 8.x | Godis 状态 |
|---|---|---|
| `SET` 选项 | `KEEPTTL`、`GET`（6.2+） | 仅支持 `NX/XX/EX/PX` |
| `GETEX` | 支持 `EXAT/PXAT` | 缺少 |
| `BITOP` | AND/OR/XOR/NOT | ❌ 未实现 |
| `SMOVE` | — | ❌ 未实现 |
| `BRPOPLPUSH` | — | ❌ 未实现 |
| `HEXPIRE/HPEXPIRE/HEXPIREAT/HPEXPIREAT` | Redis 8 Hash Field TTL | ❌ 未实现，只有 `HGETEX/HSETEX/HGETDEL` |
| `HGET` | 单字段 | ⚠️ 被重复注册，`database/hash.go:605` arity=3 被 `:619` arity=-3 覆盖，导致允许多参数 |
| `ZRANGE` | `BYSCORE/BYLEX/REV/LIMIT` | 仅 `[start stop] [WITHSCORES]` |
| `ZRANK/ZREVRANK` | `WITHSCORE`（7.2+） | 不支持 |
| `XCLAIM` / `XAUTOCLAIM` | 消费者组 | ❌ 未实现 |
| `WAIT` | 复制确认 | ❌ 未实现 |
| `UNWATCH` | 事务 | ❌ 未实现 |
| `CLUSTER MEET/ADDSLOTS/DELSLOTS/SETSLOT/REPLICATE/FAILOVER/...` | 15+ 子命令 | ❌ 仅实现 5 个 |
| `CLIENT SETINFO/NO-EVICT/NO-TOUCH` | 连接管理 | ❌ 未实现 |
| `FUNCTION RESTORE` / `FCALL_RO` | 函数 | ⚠️ 注册名是 `Function|Restore`、`FCall|RO` |
| `VS.DROPINDEX` | Vector Set | ❌ 未实现 |
| `FT.SYNADD` | RediSearch | ❌ 只有 `FT.SynUpdate/SynDump` |
| `TD.*` 族 | T-Digest | ⚠️ 注册为 `TDigest.*`，且大量子命令缺失 |

### 2.4 运维 / 管理命令大量桩实现

- `INFO`：`database/systemcmd.go` 中 `master_repl_offset`、`rdb_last_save_time`、`blocked_clients`、`pubsub_patterns` 等大量字段为 0 或 TODO。
- `CLIENT LIST/KILL/INFO/ID/UNBLOCK/REPLY/CACHING`：大多是硬编码或 no-op。
- `CONFIG GET/SET`：仅支持少量配置项，缺少 `maxmemory` 等关键项。
- `MEMORY USAGE`：固定返回 0。
- `PUBSUB CHANNELS/NUMSUB/NUMPAT`：桩实现返回空 / 0。
- `CLUSTER NODES`：硬编码 `127.0.0.1:6379`，不反映真实拓扑。

## 3. 集群、ACL、复制、持久化

### 3.1 集群：可用骨架，生产差距大

- **子命令覆盖极低**：仅 5 个 CLUSTER 子命令（`NODES/INFO/SLOTS/KEYSLOT/HELP`）。
- **槽位数不一致**：`cluster/core/utils.go:15` 内部 `SlotCount = 1024`，但对外命令和 pub/sub 却使用 `16384`，客户端槽位计算会错。
- **数据迁移半实现**：`cluster/core/rebalance.go` + `node_manager.go` 有真实迁移流程，但缺少 `ASKING/ASK/MOVED` 重定向、迁移期间写保护、失败回滚、跨节点 `SPUBLISH` 转发。
- **Sharded Pub/Sub**：槽位用自定义哈希，不是 Redis 的 CRC16；`SSubscribe` 传入 `nil` 连接，无法按客户端跟踪。

### 3.2 ACL / Auth：引擎已启动，但权限粒度不够

- `InitACLEngine()` 在 `database/server.go:172` 被调用，`Server.Exec` 也调用了 `checkACLPermission`。
- **但 ACL 仅检查命令名**，不检查 key pattern、channel、selector：
  - `acl/acl.go` 有 `CheckKey`、`Channels`，但从未被调用。
  - `cluster/core/command.go` 完全没有 ACL 检查。
  - `ACL DRYRUN` 只检查命令名。
  - `ACL LIST/GETUSER` 不输出 key/channel/selectors。
  - Redis 7/8 的 **ACL selectors** 未实现。

### 3.3 复制：基础 PSYNC 有，但缺少 WAIT

- 已实现 `PSYNC`、全量/增量同步、`REPLCONF`、复制积压缓冲区。
- **没有 `WAIT` / `WAITAOF`**。
- `replId` 来源不一致：`replication_master.go` 用随机串，`systemcmd.go` 用 `RunID`。
- 积压缓冲区只是不断 append 的 `[]byte`，没有真正的环形缓冲。

### 3.4 持久化：只覆盖基础类型

- **AOF marshal**（`aof/marshal.go:21-34`）仅支持 string/list/set/hash/zset，**不支持 bitmap、stream、JSON、vector、timeseries、概率数据结构**。
- **RDB 加载**（`database/persistence.go:46-94`）同样只处理基础类型。
- RDB aux 字段 `redis-ver` 硬编码为 `6.0.0`（`aof/rdb.go:119-123`），与 Redis 8.x 的 RDB 版本 11/12 不符。
- AOF rewrite 不是 fork/COW，而是单进程暂停写入后重写。

## 4. 测试与 CI：全绿但覆盖面不足

- `go test ./...` **全部通过**。
- **覆盖率不均**：`aof` 1.5%、`cluster/core` 1.5%、`redis/protocol` 0%、`redis/connection` 0%、`pubsub` 0%、`datastruct/json|vector|timeseries|probabilistic` 0%。
- **没有 Redis 8.x 兼容性回归套件**：CI 中的 Redis 8 sidecar 只用于启动 Godis 做 smoke test，没有把 Godis 输出与真实 Redis 输出逐项对比。
- **Fuzz 仅 parser**：`redis/parser/fuzz_test.go` 有，但 RESP3 解析器、AOF marshal、协议编码都没有 fuzz。
- **Race detector 未覆盖关键包**：`race.yml` 虽已扩展，但仍未覆盖 `redis/server/*`、`datastruct/*` 等。

## 6. 建议的最小可行实施顺序

1. **S0（半天）**：仓库卫生——`.gitignore` 去掉二进制/覆盖率残留、归档历史报告。
2. **S1（2–3 天）**：命令分发修复 + HGet/Rename/模块 key metadata bug + RESP3 协议版本连接字段 + HELLO 写状态。
3. **S2（3–5 天）**：RESP3 请求解析器接入 std/gnet + 回复按版本选择编码 + Attribute/Map 完善。
4. **S3（5–7 天）**：补齐 Redis 8.x 关键命令（HEXPIRE、BITOP、SMOVE、XCLAIM、WAIT、UNWATCH、CLUSTER 子命令）。
5. **S4（并行）**：ACL key/channel 权限检查、AOF/RDB 扩展新类型、INFO/CONFIG 字段填充。
6. **S5（持续）**：Redis 8.x 响应比对测试 + fuzz + 覆盖率提升 + 文档同步。

## 7. 总结

- **协议层**：RESP2 可用；RESP3 只有类型定义，没有端到端能力，是当前最大的“虚假宣传点”。
- **命令层**：约 70–85% 覆盖，但模块命令的分发方式与标准 Redis 客户端不兼容，且存在多个明显 bug 和大量桩实现。
- **集群/安全/持久化**：骨架完整，但距离生产可用差一个量级；槽位数不一致、ACL 粒度过粗、持久化不支持新类型是最突出的风险。
- **测试**：`go test ./...` 全绿，但缺乏与真实 Redis 8.x 的响应比对，覆盖率在新特性上严重不足。

建议短期内把 **“RESP3 端到端 + 命令分发标准化 + 关键 Redis 8.x 命令补齐”** 作为核心目标，而不是继续扩大命令表宽度。
